Foundations

DoneFeaturesFlow 2.1–2.8, 2.27PROJECT.md §9CLAUDE.md

Problem

Every feature needs the same plumbing: where its code lives, who may call it, how a session is recognised, how the first administrator gets created, and how two writers avoid overwriting each other. If that is settled once, each feature handler stays short and reads the same way.

Approach

A single ASP.NET Core project organised as vertical slices. Access, authentication and persistence rules live in a few shared places, and each handler calls them the same way. Dashboard, projects, members and user accounts (2.5–2.8, 2.27) are ordinary slices built on these pieces. They aren't covered separately.

Code walkthrough

One folder per area, one class per use case

Features/<Area>/ holds a static class per use case with a Handle method, plus an <Area>Endpoints.cs that maps them under /api. Program.cs registers each area with one line (api.MapTestRunEndpoints()). Handlers return TypedResults inside a Results<…> union.

Inferred The union puts every possible answer (404, 403, 409) in the method signature, so the OpenAPI document and a reader see them without reading the body. Slices keep a feature's files together, which fits a solo developer who moves between features often.

404 for outsiders, 403 for Viewers

Every project-scoped handler starts with ProjectAccess.RoleAsync. It returns the caller's role, or null when they aren't an active member. Null becomes 404, never 403, so a project's existence doesn't leak. A Viewer who tries a mutation gets 403. The query also ignores removed members and archived projects, so neither has to be checked again in each handler.

A cookie for the browser, a bearer token for API clients

A policy scheme reads the Authorization header. Bearer (ordinal match) goes to Identity bearer tokens, which last 15 minutes and are meant for the planned mobile viewer. Anything else goes to the HttpOnly, Secure, SameSite=Lax cookie PROJECT.md §9.2.

The fallback policy requires a signed-in user without a pending password change. Every endpoint is protected unless it opts out with AllowAnonymous or AllowPendingPasswordChange, so forgetting an attribute fails closed. The cookie answers 401 and 403 instead of redirecting to a login page the API doesn't have. The security stamp is re-checked every minute, so a password change ends other sessions quickly.

No default credentials: a one-hour setup link

The first SuperAdmin is created through a "PocketBase-style" link rather than a seeded account PROJECT.md §9.1. While no SuperAdmin role exists, startup prints a link holding 32 random bytes as hex. The token lives only in memory and expires after an hour. It travels in the URL fragment (/install#token=…), which browsers never send to a server, so it stays out of request logs. The comparison runs in constant time.

Setup can only happen once

Two people could open the link at the same moment. The handler checks the role and the token, then takes a PostgreSQL transaction-level advisory lock and checks both again inside it. This is a double-checked lock: the cheap check turns most requests away early, and the locked check is the one that decides. The SuperAdmin role is the permanent marker, so deleting or disabling the administrator never reopens setup.

A deletion policy that protects history

Every relationship is configured in OnModelCreating. Catalog references (endpoint, spec, project) use Restrict, so a past run's evidence can't vanish because its endpoint was deleted. Only data a TestRun owns cascades. Links between those owned rows use NoAction "to avoid multiple cascade paths": a finding is owned by its run and also points at its execution, and only the run's cascade should delete it. JSON payloads are jsonb.

Project members are soft-removed (RemovedAt). Re-adding someone reactivates the same row, keeping JoinedAt PROJECT.md §9.3.

Logs that keep secrets out

One summary line per request, with the path only. A query string can carry an API key. Simulator paths are cut short because their token is the route's only key (§8).

The frontend shell loads in the browser only

The (app) route group turns off server-side rendering. The HttpOnly cookie reaches /api only through the browser, so a server-side load would arrive signed out. The layout sends signed-out users to /login and users with a pending password change to /setup. That mirrors the backend's fallback policy, but the backend still enforces it.

Trade-offs and limits

  • The permission matrix (what each role may do beyond Viewer = read-only) is still [Open] FeaturesFlow 2.8.
  • Results<…> takes at most six types, so ImportSpec folds its refusals into one slot (comment at ImportSpec.cs:13).
  • Identity failures are reported by error code, never by description (CLAUDE.md). Inferred Descriptions can echo user input or internals; codes are stable for the frontend to translate.
  • Scalar and the OpenAPI document are mapped only in Development.
§1

Target and credentials

DoneFeaturesFlow 2.9, 2.12PROJECT.md §9.0

Problem

ChaosLab sends real requests, writes included, to someone's API using their credentials. It must only hit a target the user says they may test. Nobody should be able to point it at cloud metadata endpoints or other hosts. And the secret must never show up again: not in the UI, logs, reports, or a request to a different host.

Approach

  • An explicit authorization step. Saving a target requires confirming that you own it or may test it, and that it is not production. The confirmation is recorded again whenever the base URL changes. The preflight refuses to start a run without it (§6).
  • Encrypted at rest, tied to its row. Bearer, API key and Basic credentials are stored with AES-256-GCM. The key comes from configuration, not the ASP.NET Data Protection key ring, because it must survive restarts and container recreation. Only the last four characters are ever shown.
  • One address guard for every outbound request: spec fetches, connection checks, runs and the simulator's forwarding.

Code walkthrough

The row id is part of the encryption

The owning row's id is passed as GCM associated data. A ciphertext copied onto another row (another project's environment, say) fails authentication and won't decrypt. A missing key fails only when a secret is touched, so endpoints that never handle one keep working.

Check the address at connect time, not at validation time

Checking a URL when it's saved isn't enough. A redirect or a DNS answer that changes between check and connect (DNS rebinding) would slip past. The guard runs inside ConnectCallback on every resolved address of every connection. Proxies are ignored, because the callback would only see the proxy's address. There's no cookie jar, because the handler is shared across projects and would replay one target's session into another's requests.

Blocked addresses are link-local (including 169.254.169.254), known cloud metadata hosts, and NAT64-wrapped versions of them. Private and loopback addresses are allowed on purpose, because test targets are usually internal (comment at ImportSpec.cs:52).

Credentials never leave the target's origin

The runner's clients reuse the same guarded handler with redirects turned off, so a 302 can't carry an Authorization header to another host. Paths come from the spec, which the user doesn't fully control. Combine refuses any joined URL whose scheme, host or port differs from the base URL.

Trade-offs and limits

  • Changing Credentials:Key makes every stored credential undecryptable. TryUnprotect returns null and users re-enter them. The install script must never overwrite an existing .env for this reason (§15).
  • Allowing private and loopback hosts means anyone who can configure a target can make ChaosLab call an internal service. That's accepted, because that's where test targets live.
  • TLS verification can be turned off per environment for self-signed test servers.
  • Secret redaction, retention and telemetry sanitisation are still an open decision PROJECT.md §25 item 16.

OpenAPI import and re-import

DoneFeaturesFlow 2.10, 2.25PROJECT.md §5.1

Problem

The spec is ChaosLab's only description of the API. Import has to accept pasted text, an uploaded file or a URL, in JSON or YAML, as OpenAPI 3.x (Swagger 2.0 is converted). It must reject a broken document with errors that point to the place in the document. When the API changes, a re-import must not throw away the user's choices, test values or scenario edits.

Approach

SpecDocument wraps the Microsoft.OpenApi reader with its YAML extension and a 5 MB cap. It reports issues with dotted locations such as paths./refunds.post.requestBody. The spec row keeps the original text, the parsed document as jsonb, and a SHA-256 hash. Endpoints whose required inputs can't be filled are reported as warnings, not errors (NEI-58), so an imperfect spec still imports.

Code walkthrough

Only real paths become endpoints

Keys under paths that don't start with / are extensions, not operations. Treated as a path, x-@evil.test would turn https://api.test + path into a request to another host. Path length is capped too.

A re-import carries the user's work over

The same document again is a no-op, since a new version would change nothing and drop the scenarios. Otherwise, each endpoint's testing choice and saved test values are copied from the old spec by (path, method). The old spec is retired before the new one is inserted, because a unique index allows only one active spec per project and PostgreSQL checks it per statement.

Let the database settle races, and re-sync scenarios in the same transaction

Two imports at once can't both win: the loser hits the unique index and gets 409. A first import generates no scenarios; the user starts generation from the Scenarios page. A re-import of a spec that already had scenarios runs the generation rules on the new endpoints, carrying edits over (§4), inside the same transaction. The project is runnable as soon as the import commits.

Trade-offs and limits

  • There is no preview or diff before a re-import is saved. Re-importing the old document undoes it FeaturesFlow 2.25.
  • Only local $refs are resolved; external references are not followed.
  • A URL import has a 15-second timeout and the same 5 MB cap. Only parse issues are returned, never the fetched body.
  • Past runs are unaffected by a re-import: each execution keeps a snapshot of what it ran (§6).
§3

Endpoint discovery and selection

DoneFeaturesFlow 2.11PROJECT.md §26 (24 Nov)

Problem

Not every operation should be hit. Some must never be tested, such as "delete account" or "charge card". The ones that are tested need valid requests: required path, query and header values and a body. Specs often don't include examples.

Approach

Each endpoint has a Testing state: Included, Excluded or NeverTest. For missing inputs, the decision of 24 November 2026 introduced test values. Owners and editors save them per endpoint. The runner sends a saved value first, then the spec's example, default or enum value. Nothing is guessed at run time, "because ChaosLab sends real writes".

Rejected alternatives PROJECT.md §26:

  • Generating missing values at run time with no user step. Guessed values often fail validation, and writes go out unreviewed.
  • Saved values without a schema draft. That's too much typing for large specs.

Code walkthrough

A complete handler, start to finish

This is the shape of most mutations: access check (404 or 403), input validation, a lookup scoped to the project's active spec (an old endpoint id from a stale page answers 404), then the change.

One function decides what gets sent

TestValues.Fill is shared by the runner, the import warnings and the spec page, "so the three can't drift apart". A saved value wins over the example. An Idempotency-Key header needs no value, because the runner sends a fresh one on every request. Whatever is still missing is reported by label, and the scenario fails as a runner problem that points to the endpoint list.

Draft from schema, but never send a draft

The frontend's Draft from schema fills the body editor from the body's schema (required properties, types, enums, formats). The user reviews and saves it; nothing is sent until it is saved. Self-referencing schemas stop at null instead of recursing forever.

Trade-offs and limits

  • Optional and cookie parameters are never sent (// shortcut: at TestValues.cs:47).
  • Test values are not credentials and are stored in plain text. Authentication belongs in the environment's encrypted credentials (§1).
  • A required body with no JSON media type (multipart, form) can't be sent, and no test value fixes that.
  • How stateful endpoints are prepared, cleaned up and safely re-run is still open PROJECT.md §25 item 5.
§4

Scenario generation

DoneFeaturesFlow 2.13PROJECT.md §8

Problem

Applying all nine chaos primitives to every endpoint produces noise: a malformed-JSON test on an endpoint with no body, or a retry storm against a non-idempotent POST. Each scenario should exist for a reason drawn from the spec, and the user's edits should survive regeneration and re-import.

Approach

The conceptual model is Scenario = Endpoint × Applicable Fault × Parameters × Auth state × Expected behavior PROJECT.md §8. ScenarioGenerator.For is a pure function of one endpoint and the spec. It reads the method, declared responses, response media type, an Idempotency-Key header, and security. It returns plans: one per applicable fault type, each with default parameters, a recorded reason and a default on/off. Small APIs aren't padded; large specs can reach the 100+ design target.

Code walkthrough

Rules that follow from HTTP semantics

Latency and Timeout / Drop apply everywhere. A 5xx storm is only generated where retrying is safe: idempotent methods, or a POST or PATCH that declares an Idempotency-Key. Every operation can be throttled, but 429 is only on by default where the spec declares it.

Rules that read the spec's shape

Body faults need a 2xx response with a body. Malformed JSON also needs a JSON media type. Auth Expiry needs a security requirement. Declaring 502, 503 or 504 suggests the endpoint calls a dependency, which is where Dependency failure applies. Slow Drip and Dependency failure start off, because they need a large body or the simulator in the target's path. Duplicate Request applies to POST, PUT and PATCH, with the same key when the spec declares one.

Sync, don't regenerate

SyncAsync brings stored scenarios in line with the rules without wiping them. An existing scenario only gets its reason refreshed. A new one takes the parameters, default and invariants of the matching scenario in the previous spec, if there was one. A scenario the rules no longer produce is removed, unless a run already used it; history keeps it.

One table of allowed parameters

Users can tune parameters, so the server validates them against one table per fault type. Optional fields like path and requests were added later. Left out, as in every scenario stored before them, they keep the old behavior, so existing projects and past runs are unchanged. The frontend's field ranges mirror this table (scenarios.ts, line 1).

Trade-offs and limits

  • Moving four faults into the dependency path was done with an optional path parameter. Four new scenario types, generator rules and labels for the same faults were rejected PROJECT.md §26 (25 Nov).
  • The default Auth Expiry credential is expired, which can't be minted from outside. The runner sends an invalid one in its place (§8).
  • The final applicability rules and the duplicate-request safety conditions are still open PROJECT.md §25 items 6, 7.
§5

Developer invariants

DoneFeaturesFlow 2.14PROJECT.md §13

Problem

Built-in rules can't know business rules. "Two identical POST /orders create at most one order" or "inventory never goes negative" can only come from the developer.

Approach

Invariants are structured assertions, a type plus params configured in the UI. They are not free text and not an expression language PROJECT.md §26 (8 Nov). There are six types. An optional read-back GET checks the resulting state; its path can use {{request.body.<field>}} to reach the record just written. Invariants are saved on the scenario and snapshotted per execution. A violated invariant makes the finding Fail. One that can't be checked is reported as not evaluated and doesn't change the outcome.

Inferred A closed set of types keeps evaluation deterministic and each failure explainable in a sentence. It also keeps user-written code from running inside the runner.

Code walkthrough

The shape: six types, flat params, optional read-back

Validation tied to the scenario

Some rules only make sense in context. A record count after duplicates applies only to Duplicate Request scenarios and needs a read-back to count with. A read-back is always a GET to a path starting with /, so it can't become a second write or leave the target.

Which response an invariant is checked against

With a read-back, the read-back's response is checked; otherwise, every faulted request is. Timeout / Drop is the exception: the runner ended that request itself, so there's nothing to check. A violation anywhere wins, then "not evaluated", then the first result.

Trade-offs and limits

  • The read-back is sent right after the last response, so a target that writes asynchronously may not show the record yet (// shortcut: in RunExecutor.cs).
  • Only the first 16 KB of a body are stored, so a longer one doesn't parse for field invariants.
  • The record count reads a top-level array, or the only array inside a top-level object. Deeper nesting needs a records path that doesn't exist yet.
  • The final list of types is still open PROJECT.md §25 item 11.
§6

Run configuration and preflight

DoneFeaturesFlow 2.15PROJECT.md §26 (8 Nov)

Problem

A run sends real traffic, possibly writes, to someone's system. Before anything is queued, ChaosLab needs to know: is there a spec with included endpoints, an authorized target, a reachable server? Has the user agreed to state-changing requests? And a past run must keep meaning the same thing after the scenarios, test values or environment are edited.

Approach

The New Run page calls preflight, which lists blockers. Credential problems are only warnings, since a stored validation can be stale and some operations need no credential. CreateRun then re-checks everything on the server, so the page's checks are advisory. Concurrency is 1 to 5, one at a time by default PROJECT.md §26 (8 Nov). Runner retries are 0 to 3. The run stores scoring version 1.0 and a configuration snapshot, then waits as Queued for the runner.

Code walkthrough

Blockers as plain sentences

Each blocker is the sentence the page shows, telling the user what to do next.

Confirm writes, and probe the target last

Scenarios that call POST, PUT, PATCH or DELETE, or that send duplicates, need confirmStateChanging. The frontend has the same rule (needsConfirmation in runs.ts), but only the server's check counts. The reachability probe runs right before the insert, "so nothing runs against a target that is down".

Snapshot everything a run depends on

The run stores its target, options and selection in RunConfig. Each execution copies its scenario's parameters, invariants and the endpoint's test values. Later edits, a regeneration or a re-import can't change what a past run sent or how it is read. The run is created Queued; nothing executes inside this request.

Trade-offs and limits

  • A selection that no longer matches the included endpoints (a stale page) is rejected with "Reload and try again" rather than silently trimmed.
  • Runs always target the project's default environment.
  • Headers and credentials are not snapshotted. The runner reads them live, because after a move to another host they belong to that host (comment in RunExecutor.cs).
§7

Execution

DoneFeaturesFlow 2.16PROJECT.md §10.3

Problem

A run takes minutes and can't live inside an HTTP request. Execution must survive a database that isn't up yet and never start a run twice. It must keep ChaosLab's own bugs apart from the target's failures, and run scenarios side by side without them interfering.

Approach

RunExecutor is a hosted service that polls for Queued runs every two seconds, oldest first. It keeps three kinds of failure distinct everywhere PROJECT.md §10.3:

  • The target failed: a legitimate result, evaluated and scored.
  • The runner failed: never counted against the target, and retried a limited number of times.
  • The target was unreachable: the scenario is skipped with a reason and left out of the score.

Every request is stored as an HttpObservation as it finishes, so the live view shows progress. Each one carries its runnerAttempt.

Code walkthrough

A loop that survives outages

On first start, and after any failed tick, RecoverAsync fails runs left Running by a dead process; nothing else will ever finish them. An outage is logged as an error once, then at debug level, so a database that's down doesn't flood the log. A tick that took a run loops immediately instead of sleeping.

Claim a run with a conditional update

Read the oldest queued id, then flip it Queued → Running only if it is still Queued. If the user cancelled in between, zero rows change and the run is never started. This "compare-and-set in SQL" pattern (ExecuteUpdateAsync with the expected state in the WHERE) replaces read-then-write everywhere state can change concurrently.

Lanes: concurrent, but never on the same endpoint

With concurrency above 1, each endpoint becomes a lane whose scenarios run in sequence order, and up to concurrency lanes run at once. Two scenarios on one endpoint never overlap, because they would count each other's records. Scenarios in the dependency path wait until every lane is done and then run alone, because an armed simulator affects every call through the environment's route (§8).

Runner retries apply to runner failures only

An exception inside the runner is ChaosLab's problem. The scenario is tried again after one second, up to the run's limit, unless the run was cancelled. Target failures, unreachable targets and requests the spec can't fill are results, so they are never retried. Requests from a failed try stay on record, and the evaluator judges the last try only.

Trade-offs and limits

  • // shortcut: one run at a time for every project, so a long run holds up other projects' queues.
  • // shortcut: recovery assumes a single backend instance; with several, runs would need a lease.
  • Side by side, the target carries more load, so timings can read slower than they would alone FeaturesFlow 2.16.
  • The final status is Completed when every scenario ran, PartiallyCompleted when some did, and Failed when none did. Only Completed runs are scored (§11).
§8

Fault placement

DoneFeaturesFlow 2.16PROJECT.md §10.1, §10.2

Problem

A fault only tests the target if the target meets it. A 503 swapped into the runner's own response shows that the fault was reproduced, not how the API handles a failing dependency. Where each fault is applied decides what a result can prove, and this is the least obvious part of the design.

Approach

The baseline is "direct-first, with a supporting proxy or simulator" PROJECT.md §10.1. There are three mechanisms:

Decisions of 15 November 2026 about the simulator PROJECT.md §10.2:

  • A backend route, not its own listener. Nothing new is deployed, and arming is a memory write. Given up: a refused TCP connection, which only a separate listener could produce.
  • YARP's IHttpForwarder does the forwarding, for its handling of hop-by-hop headers and streaming.
  • Fenced off from browsers, because the route sits on ChaosLab's origin.
  • The key is a revocable 64-character token, not the environment id. It is rotated when the dependency URL changes or an owner or editor is removed or made a Viewer.
  • A capped call log, so a retry loop can't grow memory without bound.

Code walkthrough

Direct faults are the runner's own behavior

Latency waits before sending. Timeout / Drop sends a body that stalls, then a normal recovery request, which is the actual evidence: did the target get over the abandoned request? Duplicate Request fires copies with staggered starts, like a double submit, and the same, different or no idempotency key.

The injector: a pure function, no proxy

The proposal was YARP as an HTTP proxy. What got built is simpler: the injector runs in process with no listening port, and it's a pure function. The target is called for real; the injector decides what the runner is shown instead. A listening proxy is only needed once something other than the runner must reach it, and that's the simulator.

Keep both truths on the observation

The upstream status and body stay the target's own. The client status and clientBody are what the runner was made to see, marked ModifiedResponse. The evaluator always judges the target's status, and the timeline can show both. The fault works on the redacted body, so cutting it can't leave half a secret behind.

The simulator: forward until armed

Applies decides the placement: Dependency failure always, and the four injector faults when their path is dependency. The route looks the environment up by token, and an unknown token or missing dependency URL gets 404. With no fault armed it simply forwards. With one armed, the fault either answers the call itself or lets it through to be changed on the way back. Each call is logged on arrival, because the target may answer the runner before the call ends.

Two kinds of "down"

A fast failure and silence can be handled differently by a target, so the two settings behave differently. unresolvable closes the connection at once. unreachable stays silent until the caller gives up or the fault is disarmed. Neither is a real DNS failure or refused connection; the target sees a closed connection either way.

Fenced off from browsers

The route needs no sign-in and sits on ChaosLab's own origin. A signed-in user who follows a link to it would otherwise send their session cookie to whoever set the dependency URL, and the dependency's answer would run as ChaosLab. So the request drops Cookie (in TransformRequestAsync), and every answer drops Set-Cookie and gets CSP: sandbox and nosniff.

Looking for a circuit breaker

Decided on 27 November 2026. Dependency failure can send several requests (generated scenarios use 5) while the dependency is down, each with its own call log. A request after the first that is answered without any dependency call means the breaker opened. An open breaker also turns away the first request after the fault. So the runner repeats the recovery request every 5 seconds for up to 60 seconds until the target answers normally, and the next scenario doesn't meet a breaker that is still open. A target that never called its dependency never met the fault, so the scenario is skipped.

Trade-offs and limits

  • The armed fault lives in memory, so ChaosLab must run as one backend instance (// shortcut: in DependencySimulator.cs).
  • Every call through an environment's route meets the armed fault, whoever caused it, so dependency-path scenarios run alone (§7). The target's dependency traffic also passes through ChaosLab between runs.
  • One HTTP dependency per environment. Changing the dependency URL rotates the token, which breaks the target's configuration until someone copies the new URL. That's intended.
  • Slow Drip in the runner's path only holds the target's connection for bodies larger than the socket buffers, which is why the evaluator needs 64 KB (§10).
  • Faults in the runner's path show the fault is reproduced, not how the target behaves. Their findings can't Pass (§10).
§9

Cancelling a run

DoneFeaturesFlow 2.17

Problem

The user presses Cancel while the runner is mid-scenario on another thread. Neither side may overwrite the other. A run that finished a millisecond earlier must not flip to Cancelled, and a cancelled run must never be scored.

Approach

There are no locks and no read-then-write. Both sides use conditional updates with the expected state in the WHERE clause, and whoever writes first wins. The runner stops starting scenarios but lets in-flight requests finish or time out. Evidence gathered so far is kept, and executions that never started become Skipped.

Code walkthrough

Cancel only what is still Queued or Running

One row updated means cancelled (204). Zero rows means either the run had already finished (409, "This run has already finished.") or it doesn't exist in this project (404). A second query tells the two apart.

The runner re-checks before every scenario

An execution is claimed only while its run is still Running. After a cancel, the claim matches nothing and the lane stops.

Leftovers become Skipped on the next tick

The cancel handler doesn't touch executions. Each tick marks queued executions of finished runs as Skipped, with a reason. The final status and score update is also conditional on Running (§11), so a cancelled run stays Cancelled and unscored.

Trade-offs and limits

  • In-flight requests are not aborted, so a cancel can take up to the request timeout to settle.
  • How a cancelled run is shown in history is still [Open] FeaturesFlow 2.17.
§10

Evaluation

DoneFeaturesFlow 2.18PROJECT.md §11.2, §12

Problem

Raw observations have to become findings a developer can trust. Each finding needs an outcome (Pass, Degraded, Fail, Inconclusive, Not Applicable), a severity, one scoring category, evidence, and wording that never claims more than was observed.

Approach

  • Pure. Evaluator takes a scenario's type, parameters, invariants and observations, and returns findings. There's no database and no I/O, so every rule can be tested with plain objects.
  • The observation philosophy PROJECT.md §11.2. Every verdict carries Expected, Observed, Suggests and Not proven, for example "retry-like behavior observed", never "uses Polly". When evidence is thin, the result is Inconclusive rather than a guess.
  • Thresholds. Those for the injector's and the simulator's faults were decided on 16 and 25 November, and the circuit breaker's on 27 November PROJECT.md §12.3. The direct-request thresholds (Latency, Timeout / Drop, Duplicate Request) are still [Proposed].
  • The worst finding sets the scenario's outcome. A judged finding outranks an Inconclusive or Not Applicable one.

Code walkthrough

Named thresholds and a named problem

Thresholds are constants with their source in a comment. Every Fail and Degraded finding also carries a Problem: what went wrong, which the scoring category alone doesn't say. A retry storm and a target that fails without any fault are both Retry findings but need different fixes (§12).

Compare with a baseline, in a fixed order

The direct-request rule compares the faulted (or recovery) request with a baseline request sent without the fault. The order of checks matters. A baseline that failed makes the result Inconclusive, because the spec's example doesn't even work without a fault. Then a 5xx or no response is Fail, a body cut short is Degraded, and "slower than 3× baseline and by more than a second" is Degraded. The second condition keeps a 20 ms → 70 ms change from counting.

Retries, read from the simulator's call log

Calls are grouped per dependency operation. More than 5 is a retry storm (Fail). Two to five calls, each at least 100 ms apart, is Pass; a smaller gap is Degraded, meaning no backoff. A single call is Inconclusive, not Degraded, because not retrying isn't treated as a defect (decisions 2–3). The worst operation decides.

Severity follows exposure

Severity is High for Fail, Medium for Degraded, Info otherwise, with one exception. An endpoint that answers 2xx without a valid credential is the only Fail raised to Critical, because it's the only rule where the failure exposes data (decision 6). A 3xx falls through to Degraded, since redirects aren't followed and carry no data.

Trade-offs and limits

  • Faults only the runner sees are Fail or Inconclusive, never Pass (decision 1). From the runner's path, Retry, Rate-Limit and Response Validation can't score above 0. The dependency path exists to fix that.
  • A Dependency failure yields up to four findings (Dependency Failure, Retry, Graceful Degradation, Circuit Breaker), a dependency-path 5xx Storm up to two, every other fault one.
  • How retries and breakers inside a separate consuming client are observed is still open PROJECT.md §25 item 3. So are the direct-request thresholds (item 8) and how baselines affect evaluation (item 10).
§11

Scoring v1.0

DoneFeaturesFlow 2.19PROJECT.md §14

Problem

The score should be one number from 0 to 100 that is deterministic, explainable, and comparable across runs. Lots of easy scenarios in one category shouldn't be able to inflate it, and a high score from thin evidence should be visible as such.

Approach

The rules are locked as scoring version 1.0 and stored on every run PROJECT.md §14.2–14.3:

  • Points: Pass 100, Degraded 50, Fail 0. Inconclusive and Not Applicable are excluded.
  • A category score is the mean of its findings, so category weights, not scenario counts, set each category's influence.
  • A category with no scored findings is left out, and its weight is shared proportionally among the rest.
  • Evidence coverage = scored ÷ (scored + Inconclusive) is shown next to the score.
  • Only a Completed run is scored. Partial, failed and cancelled runs show "not scored" rather than a provisional number.

Scorer is pure and is "the only copy of the method". Pages show what it stored; the frontend never computes a score (CLAUDE.md).

Code walkthrough

Weights as data, locked to a version

The whole method in about twenty lines

The same function scores a whole run or one endpoint; the caller chooses which findings to pass in. Dividing by the sum of the remaining weights is the proportional redistribution.

Store the score atomically, and only if still Running

A finding saved before categories were stored on findings falls back to its scenario's fault (CategoryOf). The run's status, score, coverage and category scores are written by one conditional update, and endpoint scores in the same transaction: "a run never has a score without its endpoint scores". If the user cancelled at the last moment, the update matches nothing and the run stays unscored.

Trade-offs and limits

  • Circuit breaker and fallback are evidence signals that feed categories, not categories of their own (§14.2). The Circuit Breaker finding counts under Dependency Failure.
  • Runs that finished before scoring existed are not backfilled.
  • Still open: confirming the points (§25 item 9), whether severity caps the score (item 10), and a validation plan for score sensitivity and repeatability (item 12).

Recommendations

DoneFeaturesFlow 2.22PROJECT.md §15.2

Problem

A failing finding should say what to change. The scoring category isn't specific enough: a retry storm, retries with no pause, and an endpoint that fails without any fault are all "Retry" findings, and each needs a different fix.

Approach

The evaluator names the Problem when it decides the outcome (§10). Recommender maps each problem to fixed advice: a title naming the fix, why (what the finding showed), and the fix itself. Recommendations are deterministic and rule-based, with no AI, and ChaosLab never changes the target's code PROJECT.md §15.2.

Also decided FeaturesFlow 2.22: "weak" findings aren't a separate kind. Only Fail and Degraded findings get a recommendation, because an Inconclusive finding proves nothing about the API. Each such finding gets exactly one.

Code walkthrough

A table, not a model

Each Problem has exactly one entry. A Problem without a rule throws a KeyNotFoundException instead of returning empty advice.

Saved with the finding, in one transaction

The finding, its recommendation and the scenario's outcome are written together, so none of them can exist without the others. The recommendation links to the run, endpoint, execution and finding, and records which rule produced it.

Trade-offs and limits

  • Runs executed before recommendations existed are not backfilled and show none.
  • Advice is generic per problem. It doesn't use the endpoint's details beyond what the finding already names.

§14

PDF report

DoneFeaturesFlow 2.24PROJECT.md §15.4

Problem

Results have to leave the app as a document someone can attach to a ticket. It has to match what the results page shows and never contain a secret.

Approach

  • Same queries as the page. The report "reuses the results page's queries so the report always matches what the page shows". Content comes from those queries and the run's configuration snapshot, never from request headers, bodies or credentials.
  • QuestPDF under its Community license renders the PDF.
  • Versioned files on a volume. Each generation is a new version. The PDF goes to Reports:Path, and the Reports row keeps only its file name and storage key.
  • Owners and editors generate reports for any finished run; every member can list and download them.

Code walkthrough

File first, then row, with cleanup on every failure

A row must never point to a missing file. So the PDF is written first, then the row is inserted. If the insert fails, the file is deleted. Two simultaneous generations race for the same version number, and the unique index turns the loser into a 409.

Storage keys are never user input

Keys are generated on the server as {report id}.pdf, so a request can't steer a path. Cleanup never throws, so the caller's own error is the one reported, and a file that can't be removed is logged.

Trade-offs and limits

  • // shortcut: the PDF renders inside the request. Move it to a background job if reports with thousands of findings get slow.
  • Deleting reports and retention rules are not built.
  • QuestPDF's Community license has eligibility limits. An organisation that deploys ChaosLab and doesn't qualify needs its own license FeaturesFlow 2.24.
  • An unscored run's report explains why under limitations instead of showing a number.

Shipping it

PartialFeaturesFlow 2.0PROJECT.md §26 (21 Nov)

Built: the AGPL-3.0 LICENSE; the public site in Website/ with five docs pages, deployed to GitHub Pages; migrations at startup; the image build, which serves the frontend on port 8080; the release workflow publishing to GHCR for amd64 and arm64 on a version tag; and compose.yaml. v0.1.0 was released on 26 November 2026.

Not built: the install script (install.sh).

Problem

A self-hosted tool has to install without the .NET SDK, without default secrets, and on one origin, because the session cookie is HttpOnly and SameSite.

Approach

Decisions of 21 November 2026 PROJECT.md §26:

  • License: AGPL-3.0, so a hosted copy must publish its changes. MIT/Apache-2.0 were rejected because they allow reselling as a hosted service; BSL/FSL/ELv2 were rejected because they aren't OSI open source.
  • Distribution: one release image (backend plus built frontend) and a root compose.yaml with PostgreSQL, or make up from source.
  • Migrations at startup when Database__MigrateOnStartup=true, so an image install needs no SDK. This is off in development, where make migrate stays.
  • One origin. The frontend is built with adapter-static and served by the backend with an index.html fallback, so the cookie works without a proxy.
  • A separate public site (Website/) rather than a route in the app, so instances never serve marketing.

Code walkthrough

Migrate before the runner starts, and fall back to the SPA

Migrations run before the host starts, and with it the run executor, so the runner never polls an old schema. Every non-/api path gets index.html. Unknown /api paths get no page: 401 when signed out (the fallback policy applies) and 404 when signed in.

Compose: secrets from .env, data on volumes, loopback only

Compose refuses to start without CREDENTIALS_KEY and POSTGRES_PASSWORD (:?), so there's no fallback default. Sign-in keys and reports live on volumes, because without the keys every recreation signs everyone out. The port binds to loopback only: Secure cookies work over plain HTTP on localhost in Chrome, Edge and Firefox, but never in Safari. Anything beyond that needs an HTTPS reverse proxy.

Trade-offs and limits

  • The planned install script writes .env only if none exists. A new key or password would orphan the database and every stored credential (§1).
  • docker compose pull doesn't update compose.yaml itself. When a release changes it, download it from that release's tag.
  • CLAUDE.md still says the frontend uses adapter-auto. The decision log and package.json say adapter-static, so that note looks stale.
